# Red Hat Summit 2027 — experiment evidence map

**Scope:** Laboratory demonstrations of stale-state handling for Kubernetes Deployment desired replicas and Red Hat Ansible Automation Platform (AAP) workflow approval routing. The local Ansible/kind A/B control now also has a public, author-triggered GitHub-hosted CI execution; the historical AAP runs remain author-reported. This is a guide to existing evidence, **not** a new benchmark, production case study, independently authored experiment, or independent human review.

## Read this first

These experiments are **different series**. Their numeric observations must not be combined as if they came from one workflow or cluster.

- **Native AAP series:** AAP invokes `kubernetes.core.k8s` directly. The AAP workflow's conflict classifier examines the Ansible module error for a Kubernetes API `409 Conflict` and deliberately fails the job to take a failure edge. Its underlying job exports and effective cluster endpoint are **not public**; the job outcomes below are **author-reported**.
- **Earlier adapter series:** AAP calls an author's restricted localhost adapter which applies changes to a **kind** cluster. An HTTP 409 recorded at that adapter boundary is **not** proof that AAP itself received a raw Kubernetes API-server 409.
- **Standalone kind API controls:** No AAP approval nodes, credentials, workflow routing, or OpenShift are involved. HTTP outcomes below are from the local Kubernetes API calls as reported in preserved receipts.

## Key module implementation distinction (pinned source and local Ansible/kind runtime control)

In the upstream `kubernetes.core` **6.4.0** `k8s_scale` module, `resource_version` and `current_replicas` are checked against a fetched object before the scale operation (see [`k8s_scale.py`](https://github.com/ansible-collections/kubernetes.core/blob/6.4.0/plugins/modules/k8s_scale.py), around lines 245–286). The PATCH body constructed for the Deployment scale subresource (around lines 360–377) does **not** contain a `resourceVersion` precondition. The precondition-mismatch path warns and returns without failing a single-resource Ansible task; this must not be mistaken for a successful scale mutation. In the single-object mismatch path, the module warns and calls `module.exit_json`, which reports normal task completion without scaling. In the multi-object path it appends `changed: false` and proceeds. The `continue_on_error` option does not convert these warnings into failed tasks. This is **confirmed by reading the pinned source, not by an AAP runtime comparison**. It is not a benchmark, a new vulnerability finding, or a guarantee for all versions/options. A client-side check also leaves a theoretical interval before the unguarded scale PATCH in which state can change; that race was not experimentally demonstrated here.

The native AAP lab uses a different mechanism: `kubernetes.core.k8s` sends a JSON merge patch that includes `metadata.resourceVersion`. Its workflow explicitly maps a specifically classified conflict into a failed job and recovery branch. This illustrates why **task status and workflow routing** matter alongside optimistic concurrency.

**Local and CI runtime evidence:** The V2 Ansible/kind control demonstrates the success-vs-failure task-status distinction using `kubernetes.core` 6.4.0. [GitHub Actions run #5](https://github.com/praneethhere/aap-evidence-drift-lab/actions/runs/45236307503) executed the repository-authored four-case harness on a fresh GitHub-hosted kind cluster at commit `447d74b` and reported four case matches and `CI_REPLICATION_VERDICT=PASS`. The public job summary is inspectable; raw Ansible logs were not published. This is separately hosted machine execution, **not independent human reproduction**. Neither run demonstrates an AAP failure edge or an OpenShift outcome.

## What the evidence does not prove

No production deployment or incident; no frequency measurements; no independent reproduction of AAP runs; no independently verified human approver or separation of duties; no binding of an AAP approval decision to a cryptographically signed object snapshot; no tested HPA/GitOps-owned workload; no promise of stable desired state after read-back. The workflow's native AAP records are author-reported, and the actual OpenShift API endpoint for those historical jobs has not been independently verified from a publicly available artifact.
